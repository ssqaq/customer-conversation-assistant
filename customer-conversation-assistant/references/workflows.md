# 专项流程

按当前任务读取需要的部分，不把所有模板同时输出。

## 专项模板

### 通用分析

| 项目 | 输出内容 |
|---|---|
| 客户情况 | 主体、相关人、所属业务、需求与条件，关键事实带依据 |
| 主要顾虑 | 明确问题、可能解释及依据、需确认的问题，不强推心理 |
| 当前进展 | 每项业务处理到哪里、已有结果、未结事项和变化依据 |
| 下一步待办 | 明确约定和建议动作分列，责任、时间、状态、业务与来源明确 |
| 回复草稿 | 直接可用的正文，必要依据和待核实说明另写给用户 |

### 业务语境

| 语境 | 选用字段和进展 | 回复重点 |
|---|---|---|
| 销售或采购 | 需求范围、报价口径、试用评估、采购条件、付款交付，记录实际存在的环节 | 回答选型采购问题，不默认成交率目标 |
| 咨询或项目合作 | 目标、范围、成果、分工、费用、变更、验收，按实际进展描述 | 对齐范围责任与交付，不强行推动签约 |
| 售后服务 | 订单、诉求、发生情况、已处理事项、证据材料、适用政策和处理结果 | 分清申请、批准、处理和最终确认，不编承诺 |

以上是语境示例，不是行业白名单、互斥分类或固定步骤。各行业可以沿用用户材料中的行业词汇，但沟通整理不替代医疗、法律、金融、保险等专业或监管结论；没有适用来源时只列待核实问题。具体例子：

- 软件采购有使用人和采购人时分别记录；预算只说“别太贵”时不估一个数字。
- 装修从 8 万明确改为 12 万，写当前预算和变更依据；不同工程范围报价不能直接比较涨幅。
- 售后客户要求退款，只记退款诉求；“已经批准”不等于到账。
- “旧设备先修好，再谈续约”分别记录维修与条件性的续约意向；不要写已续约。
- 投诉订单 A 后询问另一型号，售后与新购买咨询分开；没有新订单号只用本地业务标签。
- 同一订单认可改期又问增购，更新原业务交期、另列增购诉求；有新业务依据才新建业务标签。

### 按任务选输出

| 任务 | 内容 |
|---|---|
| 客户档案 | 主体与身份依据、联系人、业务索引，分业务需求条件进展顾虑、来源和待确认信息 |
| 顾虑与异议 | 原话背景、明确关注点、可能解释及依据、澄清问题、参考回应 |
| 提取待办 | 业务、事项、责任方、约定时间、状态、来源；建议动作另列 |
| 回复或重新联系 | 当前目标、前情和未结事项、自然草稿；有实际区别时才给备选版本 |
| 匹配方案 | 客户要求、资料支持的选项、各解决什么问题、取舍限制与缺口；不造报价或条款 |
| 售后或争议 | 诉求、时间线、已有材料、当前状态、缺少的信息、下一步与责任方 |
| 风险检查 | 原文依据、问题性质、可能影响、核实或改写；区分接受的变更和未解释冲突 |
| 复盘与案例 | 节点、观察到的变化、回应遗漏、可能因素、可验证改进、可复用逻辑与不宜照搬部分 |
| 多客户汇总 | 各客户业务摘要、共同主题与差异、归属明确的依据、口径明确的统计和改进建议 |

回复写给客户，分析写给用户，两者分开。“资料尚缺”是内部分析结论，不把未经证实的条款塞进草稿让用户自行排雷。

## 自然得体的回复

只作用于写给客户的草稿，不改原始记录、档案证据或用户要求逐字引用的条款。一般分析仍保留五项；用户只要一句或只要正文时，按该要求交付。以下是判断方法，不是每次都要按顺序写出的套话模板。

### 先确定谁在对谁说话

从说话人、导出方和上下文确认客户、我方和第三方。客户或同事转来的记录中，“我”可能指转发者；归属无法确定且影响责任、承诺或措辞时，只确认这个信息。不要把当前助手的人设或自称带进客户草稿。

以用户指定语气和已有合适样本为先。微信、即时聊天通常用1至4句自然短话；邮件可用短段落和必要称呼，技术核对、报价或多项问题可保留清单。句数只是无明确要求时的参考，不能为了凑短删掉重要问题、条件或风险。不因“去AI味”破坏正式合同、法律措辞、技术标识或真实引用。

### 写得自然

- 直接进入客户当前的问题。删掉不传递信息的铺垫、重复结论和夸大赞美，如无实际内容的“非常理解您的心情”“赋能您的业务”“期待携手共赢”；有具体原因的感谢或道歉可以保留，不做机械禁词替换。
- 用对方已经使用的业务词和普通动词，说明具体事项。真实三项就保留三项，不为了避开排比硬删一项；不强加“不是X而是Y”、金句、比喻、整齐对仗、感叹号或装饰性标题。
- 根据内容自然分句，不刻意让每句一样长，也不故意增加错别字、口头禅、方言、表情、私人经历或戏剧性情绪来扮演真人。客户原有的正式语气和礼貌称呼正常保留。
- 报价、退款、日期和身份信息保持准确。型号、订单号、联系方式、金额、币种、单位、范围、否定与条件均是核对项，不能“润色”掉“暂定”“未批准”“预计”“不含安装”“以合同为准”等实质限制。

### 说话有分寸

- 客户表达不满时，回应其已经说出的具体遭遇或影响，例如催问多次、迟交、不能使用。没有表达情绪就不替对方判定“焦虑”“不信任”；正常询价直接回答，不必先安慰。
- 有证据证明我方失误时，简短承认具体问题，接着说明当前处理状态。责任还不明确时，承接问题并澄清事实；不为显得体贴而承认未核实责任、承诺退款或推责给其他团队。
- 不好的消息和拒绝直接说清：真实限制是什么、现有资料支持什么选择。没有折扣、替代方案或审批结果时不编。尊重客户选择，不用“为了您好”、羞辱、激将、虚假稀缺或人情压力推动决定。
- 下一步尽量只提出当前需要的一件事；多个独立问题确实都需要答复时逐项回答。已经在材料里的信息不再反复索取。没有用户明确授权时，不在客户正文新增“我去核实”“我去加急”“稍后回电”等动作承诺；可以在给用户的内部建议中列出需要做什么。用户明确授权或要求写该下一步时，才能写成将要做的动作，不能写成“已联系”“已加急”“已申请”这些并未发生的动作；新增确定期限、价格或补偿必须有依据或用户明确授权。
- 客户要求暂停、指定联系时间或渠道时照实保留；明确不再联系时，按任务准备简短确认或内部停止跟进建议，不默认附带下次追单时间。除非已有明确记录，不写“我已在系统取消提醒”等操作完成话术。

### 交付前核对

先写有依据的回复，再删掉空话，最后对照输入检查：有没有漏答、加事实、改数字或条件、把计划说成已完成、把推测说成事实、忽视联系限制。确认语气和长度符合用户要求。仅凭草稿无法核实的条款另给用户说明，正文用真实可用的表达，不把危险承诺留给用户自行删改。

默认只给一个可发送版本；用户明确要备选时再按不同语气给出，不默认展示初稿、逐句分析、评分或“去AI味报告”。用户明确要求评估文风时可以解释编辑依据，但不声称某个分数代表真实情商或保证通过AI检测。

### 客户场景示例

下列为虚构例子，只展示如何依照已给事实作答，不作为固定开场白。

| 已知记录及任务 | 合适的回复示例 |
|---|---|
| 客户说已催三次；没有确认交付时间；用户要求回应 | 您已经催了三次，抱歉让您一直等着。目前还没有确认的交付时间，今天能否交付我不能直接答复。 |
| 客户问退款是否到账；只知申请已提交、还未批准 | 目前提交的是退款申请，还没批准，暂时不能确认到账时间。 |
| 客户问能否再便宜；报价9800元、不含安装、未授权折扣 | 目前报价是9800元，不含安装，还没有确认能给的折扣。 |
| 用户要求委婉拒绝超范围工作；合同仅含报告，不含上线实施 | 这次合同包含报告交付，上线实施不在范围内；如果需要这部分，我们再确认具体工作和费用。 |
| 客户明确说不再考虑、别再联系；用户要一句确认 | 收到，后续不再跟进这项采购。 |
| 客户只问明天几点量房；原约定10:00，用户只要正文 | 明天上午10:00，按之前约定上门量房。 |

## 覆盖核对

区分工具读取范围、已知事实覆盖、未知遗漏。读完不等于理解完整，输出看起来齐全也不能证明没有遗漏。

1. 记录来源文件、批次、说话人和可用的行/消息范围；有总数、分页、缺页、工具截断标记或未收到批次时核对，继续读取可用部分，或明示具体缺口。
2. 按批次整理关键事项索引：客户和业务、预算报价变更、约定取消、完成状态、条件限制、冲突和最后确认。每项带定位依据，不只记末页或开头。内部来源可写成 `[S1] 来源标签｜说话人/文件｜时间或位置`；没有原始时间、页码或消息 ID 就写“未提供”，不要把本地标签当原系统 ID。
3. 合并时回查跨批次变化。可用“来源定位、关键事实、输出位置或处理结果、覆盖状态”的简表做核对，状态为已覆盖、待核实或超出本次问题范围。单点问题只核对相关事实，不扩大为全量报告。
4. 有独立预设事实清单时逐项比对值、主体、业务、状态及来源，不只数编号；没有清单时抽查首、中、尾和所有已知变更节点。当前执行端自行生成的清单或已见答案的测试不称独立盲测。
5. 未知完整边界或超出当前可读取范围时明确仅基于已读内容；不能承诺发现答案清单本身遗漏的事实。

重复消息规则：没有可靠会话内消息身份就保留；文字、时间、说话人一致仍不充分。可归纳同一业务相同事实并列全部依据，但无可靠去重不精确统计独立消息次数。主题频次默认数不同客户，跨客户统计范围不变成个人属性。

## 文件操作

本节仅在用户明确要求保存、建档、更新或恢复时执行。默认分析不主动生成整理后的客户文件。

### 选择动作和位置

| 用户意图 | 操作 |
|---|---|
| 分析或写回复 | 对话交付，不创建客户档案 |
| 保存这份分析 | 单份报告，不自动建长期档案 |
| 建档 | 创建客户独立目录及三个主文件 |
| 更新档案 | 先读取并确认旧档案身份和业务，再更新有依据的部分 |

用户指定目录优先，否则报告在当前工作区 outputs/，档案在 outputs/customers/。不得写入 Skill 安装目录。语义确实影响目标文件而又无法推断时，只问这个区别。

报告默认名 analysis-YYYYMMDD-HHMMSS.md，重名追加 -02、-03 等可用序号。同秒也通过实际存在检查避免覆盖。时间取保存时的真实时间，不伪作沟通时间。指定已有路径但只要求保存新报告时另取序号文件；明确更新或替换该报告时先备份再改，记录实际路径。

客户目录用安全短名加 -001 等可用序号，无姓名用 customer-001。Windows 路径移除或替换保留字符，避开设备保留名、尾部点/空格和路径穿越；不能直接把电话号码或地址拼入目录。这是路径处理，不脱敏正文。目录同名不代表客户相同，不覆盖另一客户目录。

当前任务已经打开或建立且报告过准确路径，身份与业务匹配时直接复用。仅有姓名时在用户指定目录或已知客户根目录内只读寻找候选；不能唯一确认就列候选或请求最小识别信息，不写入猜测目标。不要为找一个客户遍历全部用户目录。已有本地业务标签保持不变。

### 三个主文件

| 文件 | 内容 |
|---|---|
| profile.md | 客户主体和身份依据；联系人表；业务索引（本地标签、真实编号如有、业务短名、关联人）；分业务当前情况、依据、待确认；客户级共同事项 |
| tasks.md | 业务标签或客户级、事项、责任方、约定时间、状态及状态依据、来源；建议动作分列；完成与取消保留历史但移出未完成清单 |
| history.md | 实际更新时间、客户及业务、变更字段或事项、旧记录、新记录、来源及理由；保留事实/推测性质，不复制全量聊天代替变更摘要 |

原始姓名、联系方式及相关业务信息原样保留。用户未提及的字段不脑补。再次收到同一明确更新不重复添加待办或变更；相同文字但不同业务或时间的事项不能误删。

首次建档没有旧全套：准备完整内容后创建、回读核对；失败则说明实际生成了哪些文件并交付完整对话结果，不声称已建档，不删除输入。

### 更新前的完整快照

同一客户按单写入者处理。写入前先检查该客户 backups/ 中是否有未完成操作；发现未完成操作先按后文恢复，不覆盖旧操作记录或盲目开始另一次更新。

1. 确认客户根目录、业务身份、三个旧文件和本次完整新内容。不能仅因哈希可读取就假设客户匹配。
2. 操作标识统一用 YYYYMMDD-HHMMSS-01，实际重名时递增 -02 等；该标识同时是 backups/ 下目录名。保存完整三个旧副本，名称仍为 profile.md、tasks.md、history.md。
3. 在操作目录持久写入 operation.json：operation_id、customer_root（绝对路径）、state、restore_eligible，以及 files 下三个文件各自的 before_sha256 和 planned_sha256。state 初始为 prepared，restore_eligible 初始 true。另记实际创建时间及业务变更依据；备份中已有兼容字段时依据明确含义读取，不猜缺失字段。
4. 校验旧副本完整且哈希与刚读取的三个旧文件一致，再次检查当前文件没有新变化。任何缺失、归属不明、哈希不匹配或不可写，先停写并报告。
5. 把状态持久记为 writing，才写客户主文件。三个新内容先准备齐，逐个写入并回读。工具允许时通过同目录临时文件和原子替换完成单文件写入；不要把三文件整体称作数据库事务。
6. 三个当前文件全部达到计划新哈希后，才把操作状态记为 committed。成功回报实际路径和更新摘要。operation.json 和备份数据不属于 Skill 安装包，也不是额外客户主文件。

### 中断、恢复与重入

恢复绑定到本客户本次操作开始前的已校验完整旧副本。禁止按目录“最近”猜备份，禁止混用不同操作的三个文件。

1. 读取未完成操作与原备份，校验 operation_id 对应目录、customer_root、restore_eligible、三个文件清单及旧副本哈希。不支持恢复的旧格式、不能唯一确认的操作、缺文件、已撤销恢复资格或坏备份都停止，不猜路径或快照。
2. 读取三个当前哈希。状态尚未提交且三个文件全部符合计划新哈希、未明确要求回滚且未进入回滚流程时，可核验业务内容后完成 committed 并注明恢复确认。
3. 已进入回滚、用户明确回滚、或当前文件是本次操作已知旧/新混合状态时，使用同一旧全套整体恢复。恢复前及逐文件写入前，当前内容必须属于该操作的旧值或计划新值。
4. 任何当前文件哈希既非旧也非新，包括用户外部编辑或非原子写入产生的撕裂内容，停止自动覆盖，保留证据并逐文件报告；不要武断声称一定是用户改的。缺失当前文件同样不能当作已知旧/新状态直接覆盖。
5. 恢复前持久记录 recovery-required；使用固定旧副本恢复三个文件，逐个验证旧哈希。任一步失败保持 recovery-required，报告每个文件的实际状态；原因解除后继续同一操作，不改用另一个备份。
6. 全部恢复到旧哈希后，写操作目录下的 recovery.json，包含操作标识、原因、恢复结果、校验哈希和实际时间，再把 operation.json 标记 rolled-back。不要为记中断事件改动刚恢复并校验的业务 history.md。
7. 恢复自身中断或重复执行时仍沿同一操作核验，不重复制造业务变更。已提交或已回滚的完整操作不当成新待办；状态标记与文件不一致时报告，不直接声称成功。

恢复数据与权限都不可用时，交付已能确认的结果和失败细节，不把“尝试过”写成“已恢复”。本流程不承诺任意并发写、断电或存储设备损坏安全；发现外部改动迹象即停止覆盖。

## 更正与删除

用户提供且与业务相关的姓名、联系信息、身份信息、付款账号与金额等允许原样分析，明确保存时按任务范围写入，不强制脱敏。没有自动保留期限或自动清理任务，已保存文件保持到用户明确要求处理，不代表建议一律永久保留。

- 普通业务事实变更保留历史；用户明确要求更正错误个人信息或移除某字段时，检查本 Skill 已知档案、历史、报告、备份及待写临时副本是否含旧值，不只改 profile.md 就说全部改正。
- 客户在原聊天中要求删除，先记录为客户诉求；当前用户明确要求执行，才进入操作流程。先列明已知受影响文件和实际路径，按用户范围及平台实际删除确认要求执行。不扫描或删除其他客户、其他任务或原始微信数据。
- 范围要包含或明确排除历史与备份。不能通过先备份待删内容制造新副本，不能在后续回滚中把已删除信息恢复回来。含待删字段的备份按已确认范围处理，并撤销恢复资格；无法处理或未包含在删除范围的残留逐项说明。
- 明确禁止永久删除时按用户允许的更正或移出方式处理，不声称已彻底擦除。宿主聊天、云端副本、系统备份或其他不可访问范围不能冒称已删除。
- 更正或删除与未完成操作相遇时，先阻止该旧操作继续写入或恢复已移除内容；保留不含待删数据的必要状态说明。缺少副本清理范围或操作身份不能确认时，暂停相关写入，仍可完成独立的对话分析。

## 调用示例

- 分析这段客户聊天，告诉我现在该先解决什么，再写一句回复。
- 整理这两家客户的共同问题，分别标明各自预算，不要混成一份档案。
- 保存这份分析到我指定的目录，不建客户档案。
- 给这个客户建档，把维修和新采购分成两个业务。
- 用刚才已经保存的档案继续更新，保留这次预算调整的依据。
- 检查这个客户目录的未完成更新，先确认当前状态再按记录恢复。
- 把这段给客户的回复改得自然一点，少些套话，保留原来的数字、条件和事实。
- 客户在催进度，帮我回得有分寸，别编交付时间或处理结果。
